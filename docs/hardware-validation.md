# M1 实机媒体验收手册

本手册用于执行 M1-07/M1-08，并生成可复核的 QG-1 证据。它不会把配置值或发送端声明帧率当作观看质量，也不会自动宣称当前实现已经达到 2K60。

## 1. 验收矩阵

每种发送端 GPU 至少执行一次 1080p60 和一次 2560×1440@60fps；观看端必须使用另一台 Windows 设备。

| 发送端 GPU | 1080p60 | 1440p60 | 30 分钟 QG-1 |
| --- | --- | --- | --- |
| Intel 核显 | 待执行 | 待执行 | 待执行 |
| NVIDIA 独显 | 待执行 | 待执行 | 待执行 |
| AMD 独显/核显 | 待执行 | 待执行 | 待执行 |

客户端自动记录默认 D3D11 GPU 型号、驱动版本、Windows 版本、LiveKit SDK 版本和客户端提交 SHA。测试人员仍需记录显示器分辨率/刷新率，并在客户端中填写本次实测的 SFU 版本、上/下行带宽、RTT 和网络丢包。不要把访问令牌、窗口标题、屏幕内容或完整 SDP 写入报告。

## 2. 基准条件

- 1440p 测试使用不低于 2560×1440、60Hz 的捕获源和观看显示器。
- 发送端稳定上行不低于 30Mbps，观看端稳定下行不低于 25Mbps。
- RTT 不高于 80ms，测试前的网络丢包不高于 1%。
- 两端均确认使用 H.264 硬件编解码；若只能软件编解码，结果单独记录，不能代替硬件基准。
- 发起端和观看端时间同步。P95 端到端延迟使用画面时间标记或高速摄像测量，不能使用 RTT 代替。

## 3. 采样步骤

1. 从目标提交的成功 GitHub Actions 运行下载 `screen-share-windows-x64-<commit>` artifact，确认提交 SHA，并阅读包内 `VALIDATION-README.txt`。该包未签名，只能在专用测试机使用。
2. 将同一个 artifact 分别解压到发起端和观看端，不要直接在压缩包内运行。
3. 在两端填写相同的 SFU 版本，以及各自实测的上/下行、RTT 和基线丢包，勾选“以上网络数据已在本次运行前实测”。
4. 在发起端选择 2560×1440 捕获源，开始捕获并成功发布。
5. 在观看端加入同一房间，确认软件内画面已经稳定渲染。
6. 两端分别点击“开始 30 分钟验收记录”。发起端生成 `host` 报告，观看端生成 `viewer` 报告。
7. 运行期间保持动态桌面内容，记录是否出现永久黑屏、花屏、崩溃或 GPU 设备丢失未恢复。
8. 同时执行可重复的端到端延迟测量并计算 P95。
9. 记录到 30 分钟后客户端会自动保存；也可提前点击“停止并保存验收记录”生成失败分析材料。

报告默认写入用户“文档”目录下的 `ScreenShare/validation`。端点 JSON v2 包含构建与 GPU/驱动元数据、实测网络基线，以及每 500ms 的六段 fps、阶段累计平均耗时、码率、丢包、队列丢帧、分辨率、连接状态和进程工作集。它不包含屏幕帧、凭证、服务器 URL、会话 ID、参与者 ID 或窗口标题。

## 4. 合并和判定

在仓库根目录执行：

```powershell
node tools/qg1-evaluate.mjs --host C:\path\qg1-host.json --viewer C:\path\qg1-viewer.json --latency-p95-ms 280 --no-visual-corruption --no-crash --no-device-loss --output C:\path\qg1-combined.json
```

三个 `--no-*` 参数必须由测试人员在复查运行记录后显式提供；缺少任一参数都判定失败。工具还会检查：

- 两端均连续记录至少 30 分钟，且媒体在所有采样点保持活动；
- 两端使用相同的客户端提交、版本、LiveKit SDK 和 SFU 版本，且 GPU/驱动元数据完整；
- 发起端上行不低于 30Mbps、观看端下行不低于 25Mbps，两端 RTT 不高于 80ms、基线丢包不高于 1%；
- host 的 capture/encode/send 与 viewer 的 receive/decode/render 指标存在；
- 观看端平均实际 render fps 不低于 55；
- 两端活动样本均达到 2560×1440；
- 观看端未观察到超过 500ms 的 render 空档；
- 两端平均丢包不高于 1%，稳定期到末段的进程工作集增长不超过 10%；
- 实测 P95 端到端延迟不高于 500ms。

合并报告的 `qg1_status` 只有 `pass` 或 `fail`。端点报告始终标记为 `incomplete`，因为单台客户端无法独立证明整个链路和人工检查结果。

## 5. 失败处理

- 保留两端脱敏 JSON、合并报告和测试环境信息。
- 不在公共 Issue 上传屏幕截图、屏幕录制、访问令牌或含私人内容的日志。
- 若 1440p60 的普通原始帧路径持续无法达到门槛，按开发顺序评估预编码输入方案，然后完整重跑本矩阵。
- Intel、NVIDIA、AMD 任一基准路径未执行或失败时，M1 仍未退出，不进入 M2。
