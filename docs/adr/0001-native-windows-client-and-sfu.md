# ADR-0001：原生 Windows 客户端与 SFU

- 状态：Accepted
- 日期：2026-11-17

## 背景

产品要求观看发生在桌面软件内部，每个房间最多 20 名观看者，并在满足设备和网络基线时达到 1080p60 与 2560×1440@60fps。

## 决策

1. 使用 C++20、Qt 6 和 CMake 构建统一 Windows 客户端。
2. 使用 Windows.Graphics.Capture 与 Direct3D 11 捕获显示器/窗口。
3. 使用 LiveKit C++ SDK 作为 WebRTC 媒体客户端。
4. 使用自托管 LiveKit SFU 分发媒体，coturn 提供受限网络兜底。
5. 首版使用 H.264 硬件编解码与 simulcast。
6. 使用服务端角色令牌限制主持人发布和观看者订阅权限。

## 原因

- 纯 P2P 会使发起端上行随观看者数量增长，无法合理支撑 20 名 2K60 观看者。
- SFU 让发起端只发布少量质量层，并能为不同观看者独立选择画质。
- 原生 D3D11 媒体管线更容易控制帧拷贝、硬件编解码、渲染延迟和 GPU 设备恢复。
- 同一客户端包含两种角色，减少安装包、协议和版本组合。

## 后果

正面影响：

- 发送端带宽和编码数量不随观看者线性增长。
- 可以分别观测采集、编码、网络、解码和渲染阶段。
- 后续可在保持服务端架构的情况下替换编码输入路径。

负面影响：

- C++/Qt/Direct3D 开发和测试成本高于浏览器原型。
- SFU 和 TURN 带来显著服务器带宽成本。
- 首版只支持 Windows，跨平台需要新增平台捕获与渲染实现。

## 被否决方案

- Electron + 浏览器内观看：不符合“软件内统一观看”的最终交付目标，且对跨 GPU 的 2K60 可控性较弱。
- 纯 P2P Mesh：发起端上行和连接数随观看者线性增长。
- MCU 服务端转码：服务器计算成本高、延迟更大，首版没有合成画面的需求。
- 首版使用 AV1：硬件覆盖和兼容性不足以作为 Windows 基线。

## 复审条件

出现以下情况时复审：

- QG-1 在支持矩阵内仍无法通过。
- 生产数据证明 H.264 带宽成本不可接受。
- 需要跨平台或超过 20 名观看者。
- 需要端到端媒体加密且当前 SFU 能力不能满足威胁模型。
